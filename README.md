# hvc

视频转码与直播处理服务（Go）。

> A video transcoding and live-processing service in Go: one codebase serving standalone, cluster-control,
> cluster-worker and all-in-one modes, with MinIO object storage, RabbitMQ and Redis on the hot path.

---

## 项目定位

`hvc` 是面向视频平台的处理后端：接收转码任务 → 调度到具备相应硬件能力的节点 → 探测、计划、切片、
上传 → 发布清单 → 回调通知业务方；同时承载直播链路的推流、转码与回放。

一个项目、一个入口（`cmd/main.go`），**同一套代码**支持四种运行方式：

| 模式 | 说明 |
|---|---|
| 单机模式 | 控制面与执行面在同一进程内，适合开发与单机部署 |
| 集群控制节点 | 只做调度、租约、状态汇总，不跑转码 |
| 集群执行节点 | 只接收任务并执行，向控制节点心跳与上报 |
| 集群一体化 | 两种角色都承担，用于小规模集群 |

## 设计原则（摘自 `项目总原则.md`）

- 编码**必须硬编**；解码优先硬解，仅在源不支持硬解时允许软解；软解 CPU 总占用默认不超过 50%
- 水印、缩放、overlay 优先走硬件链路
- MySQL **只做持久化**；Redis 与低延迟通信承担热路径
- 限流、并发、热路径后端、RBAC、上传策略、故障策略都由后台动态配置控制
- 结构先定死再写代码；框架代码（go-zero / protoc 生成物）必须生成而非手写

## 任务数据流

```
提交任务 → 调度（节点/GPU 能力筛选、评分、租约）→ 执行节点：探测 → 计划 → 切片 → 上传
        → 发布（清单物化 + 逐片校验：可 GET 且 sha256 通过）→ 回调（outbox：HTTP/gRPC/MQ 任一成功即算送达）
```

状态机（转码任务）：

```
CREATED → QUEUED → ASSIGNED → RUNNING → UPLOADING → COMPLETED → PUBLISHED → CALLBACK_SENT
                                                        ↓
                                                     FAILED / CANCELED
```

- `COMPLETED` 只表示"内容已产出"；分片由**全局待传队列**异步上传，别的节点也可能在传这个任务的分片
- `PUBLISHED` 表示"清单已物化、每个分片可 GET 且 sha256 通过"，下游此刻拉取必然完整
- `CALLBACK_SENT` 表示完成回调已由至少一个通道送达，是对外承诺兑现的最终终态

## 核心能力

### 发布与回调：内容完整之后才对外承诺

- 任务在"内容已产出"之后还有两级状态：**已发布**（清单物化、每个分片可 GET 且 sha256 通过）
  与**回调已送达**；迁移只允许 `已产出 → 已发布 → 已送达` —— 下游收到回调时内容一定完整可读
- 状态迁移都用 `status` 做条件更新：多节点竞争或乱序回写不会把状态拉回
- 转码结束时**不立刻发回调**：完成载荷先落库暂存（此刻分片还在上传），落库失败退回旧行为，
  任务不会永远不回调
- 发布由两处驱动：分片上传批处理结束后**就地触发**（及时），以及复用进程内已有的 1 秒对账循环
  兜底 —— 覆盖"最后一片由别的节点上传"与"进程在两次上传之间重启"这两类没有本地唤醒的情况
- 载荷用"取 + 清"的比较交换领走 ⇒ 即使多节点同时判断"传完了"，回调也只会发一次
- 回调由 HTTP / gRPC / MQ 任一通道成功即算送达，送达后任务进入最终终态

### 断点续跑：换进程、换节点都不用从头再来

- 新增任务步骤表：`PROBE` / `PLAN` / `SEGMENT` / `UPLOAD` / `PUBLISH` / `CALLBACK` 各一行，
  记录状态、尝试次数、起止时间与产出锚点（`UNIQUE(job_id, step)`）
- 任务行记录**输入指纹**：源地址 + 切片时长/模板 + DASH/HLS 开关 + 输出存储与前缀 + 水印 +
  缩略图 + 清晰度集合；续跑条件 = 指纹一致，且步骤完成态是**连续前缀**
- 指纹变化（换源、改规格）⇒ 清空步骤行并整任务重跑，避免把上一版输入的中间产物当成新结果
- 指纹**刻意不含源文件大小/ETag**：那两项在网络抖动时可能取不到，放进去会把"这次没取到"
  误判成"输入变了"而白白全量重跑
- 日志输出一次续跑决策（指纹、是否允许续跑、各步骤完成状态），便于现场判断"重跑还是续跑、续到哪步"

### 清单与内容校验：让"回调到达"等价于"内容可拉取"

- 切片产出时即计算内容摘要并随分片行落库；发布校验要求每片摘要齐备
  （对象存储的 ETag/大小只能证明"传上去了、大小对"，证明不了内容）
- 完成回调载荷携带每个分片的摘要与大小，下游（与门禁）可据此逐片复算校验，无需信任服务端的自述
- 摘要取自分片行而非重算文件：输出目录在任务收尾会被清理，重算既慢又可能读不到

### 交付门禁 `internal/gate`

把验收判据做成可 `go test` 跑的判定，每条一个函数 + 单测，一条命令跑全部：

```bash
go test ./internal/gate/...
```

已实现 12 项检查 / 44 个用例：

| 检查项 | 内容 | 判定方式 |
|---|---|---|
| 分片可拉取且内容一致 | 清单引用的每个分片可 GET，复算 sha256 与记录一致（含 init 段） | 注入 `ObjectReader`，逐片取回复算 |
| 硬件编码 | 实际使用硬件编码器；用软编必须存在记录在案的例外理由 | 注入运行时观测（编码器名） |
| 软解 CPU 上限 | 软解路径 CPU 峰值 ≤ 50%；硬解路径标记为不适用 | 注入运行时观测（CPU 峰值与采样数） |
| 切片时长 | 每片时长与约定一致（±1s 容差；尾片允许偏短） | 纯数据 |
| 分片连续性 | 同清晰度内序号连续无缺口（重复序号同样判失败） | 纯数据 |
| 上传回执 | 每片带对象存储回执（状态 + Key + ETag + 大小） | 纯数据 |
| 载荷摘要一致 | 回调载荷声明的每片摘要与库中记录一致 | 纯数据 |
| 清单可用 | 清单可取回、容器可识别、覆盖每个清晰度 | 注入 `ManifestFetcher` |
| 回调唯一 | 同一任务只有一条完成回调事件 | 纯数据 |
| 续跑自洽 | 步骤指纹与任务一致，且完成态是连续前缀 | 纯数据 |
| 失败收敛 | 失败必带错误信息；终态不得残留错误信息 | 纯数据 |
| 进度合法 | 进度取值 ∈ [0,1000]，终态满进度 | 纯数据 |

判定原则：**只判定不修数据**。需要外部资源或运行时观测的检查一律注入，缺失时返回
`Skipped`（说明"该判却没判成"）；本次情形下本就不该判的返回 `NotApplicable`（例如软解 CPU 上限
遇到硬解路径）—— 两者都不计入通过，报告语义也分开，不会出现"全是不适用却宣称已验收"。

硬件编码与软解 CPU 上限采用**运行时观测**口径：不看配置里写了什么、也不看调度时选了什么，
只看执行期间实际观测到的编码器名与 CPU 峰值（配置与决策都可能与真实执行不一致）。
观测数据的采集与上报不在门禁内实现。

## 现状与边界（如实标注）

- **断点续跑目前能真正跳过的步骤只有上传**（它的产出是分片行，可从库中判定）。
  探测 / 计划 / 切片的产出还没有可回读的持久化形态（探测结果与计划需要写进步骤行的产出字段，
  分片清单需要一层到切片结果的转换），因此续跑时这几步仍会真的重跑。
- **门禁的判据原文未随仓库提供**（迁移脚本引用的设计文档不在仓库中）。现有 12 项检查是从设计与
  实现**推导**而来，标题均标注"（推导）"；拿到原文后按项替换即可（每项都是独立纯函数）。
- **硬件编码与软解 CPU 上限的观测数据由执行侧采集**（编码器名取 ffmpeg 实际使用的编码器取值，
  CPU 取任务执行窗口内的采样峰值）：门禁只做判定，采集与上报不在本包内；没有观测数据时返回
  `Skipped`（不算通过）。
